# ChessStation API

Серверная часть шахматной информационно-аналитической системы ChessStation. Первая версия предусматривает хранение классических партий в PostgreSQL и доступ к ним через HTTP API.

## Демо

Демо-стенд проекта доступен по адресу:

[http://201.34.159.85/chess-station/](http://201.34.159.85/chess-station/)

Backend API доступен с префиксом:

```text
http://201.34.159.85/chess-station/api/v1
```

Swagger UI для спецификации API:

[http://201.34.159.85/chess-station/api-docs/](http://201.34.159.85/chess-station/api-docs/)

Спецификация OpenAPI в формате YAML:

[http://201.34.159.85/chess-station/openapi.yaml](http://201.34.159.85/chess-station/openapi.yaml)

Ссылка на репозиторий с web-frontend:

[https://github.com/b0x009dev/chess-station-web](https://github.com/b0x009dev/chess-station-web)

На сервере доступны Swagger UI и OpenAPI. Запросы к операциям с партиями Nginx передаёт в Express, который пока отвечает `404 NOT_FOUND`. Подключение PostgreSQL и реализация этих операций предусмотрены в v1.

## Назначение проекта

`chess-station-api` – серверный репозиторий ChessStation. Его основная задача – предоставить программный интерфейс для хранения классических партий, поиска по именам игроков и работы с отдельной партией.

В v1 сервер будет принимать HTTP-запросы, проверять входные данные, выполнять операции с PostgreSQL и возвращать данные и ошибки в JSON. Для списка сервер будет выдавать имена игроков, событие, дату и результат. При открытии партии клиент получит исходный PGN для просмотра, редактирования или экспорта.

## Место серверной части в общей системе

Проект состоит из двух самостоятельных репозиториев.

- `chess-station-api` – HTTP API, проверка заголовков PGN, поиск и сохранение партий в PostgreSQL.
- `chess-station-web` – список партий и редактор, проверка ходов, импорт и экспорт PGN в браузере.

Серверная часть отвечает за хранение данных, правила их обработки и контракт API. Веб-интерфейс отвечает за работу пользователя со списком партий и редактором. Такое разделение позволяет независимо развивать, тестировать и разворачивать каждую часть системы.

На опубликованном сайте Nginx отдаёт статические файлы и передаёт запросы к API и документации в Express.

## Основные возможности первой версии

- Выдача списка партий с поиском по имени белых или чёрных и пагинацией.
- Получение партии по идентификатору. Ответ содержит исходный PGN.
- Создание, полная замена PGN сохранённой партии и удаление партии.
- Извлечение имён белых и чёрных, события, даты и результата из заголовков PGN.
- Проверка параметров и тела запроса, единый формат ошибок.

Импорт и экспорт PGN предусмотрены в браузере. Импортированная партия и партия, введённая на доске, будут сохраняться одной и той же операцией API.

## Обоснование выбранного стека

- Node.js 24 – среда выполнения серверного JavaScript.
- Express – маршрутизация HTTP-запросов и публикация документации. Для операций с партиями предусмотрены разбор JSON и централизованная обработка ошибок.
- OpenAPI, `yaml` и `swagger-ui-express` – описание HTTP-контракта, чтение спецификации и её публикация в Swagger UI.
- ESLint – статическая проверка JavaScript.
- PostgreSQL – хранилище партий и метаданных, предусмотренное для v1.

Express отвечает за приём HTTP-запросов и формирование ответов. Разбор заголовков PGN предусмотрен в сервисе, чтобы при создании и замене партии применялись одни правила проверки.

## Почему PostgreSQL для хранения партий

В v1 исходный PGN и извлечённые заголовки будут храниться в одной строке таблицы `games`. PostgreSQL позволяет использовать метаданные для поиска, сортировки и пагинации. Исходный текст остаётся доступен для просмотра и экспорта.

При создании или обновлении партии достаточно одного параметризованного SQL-запроса. PostgreSQL сохраняет исходный текст и метаданные атомарно. При ошибке не возникает частично созданной или обновлённой записи.

## Архитектура серверной части

Для операций с партиями в v1 предусмотрена слоистая архитектура.

```text
HTTP-запрос
  -> Express
  -> маршруты
  -> контроллеры
  -> сервисы
  -> репозитории
  -> PostgreSQL
```

- `routes` – описание HTTP-маршрутов.
- `controllers` – приём HTTP-запросов, вызов сервисов и формирование HTTP-ответов.
- `services` – проверка данных, разбор заголовков PGN и подготовка метаданных для сохранения.
- `repositories` – параметризованные SQL-запросы.
- Настройки HTTP и базы данных задаются через окружение. Централизованный обработчик формирует HTTP-статус и тело ошибки.

Такое разделение упрощает поддержку проекта. Правила проверки заголовков сосредоточены в сервисе и применяются при создании и замене партии. Репозиторий использует одинаковые условия для выборки страницы и подсчёта всех совпадений.

## Модель данных

Для первой версии предусмотрена одна таблица `games`. Идентификатор партии назначает PostgreSQL. Все поля обязательны. Один и тот же PGN можно хранить в нескольких записях.

### Таблица `games`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `integer` | Положительный первичный ключ партии |
| `pgn` | `text` | Исходный текст партии |
| `white`, `black` | Текст | Имена игроков |
| `event` | Текст | Название события |
| `game_date` | Текст | Дата в формате PGN. В API используется поле `date` |
| `result` | Текст | Результат партии |
| `created_at`, `updated_at` | `timestamptz` | Время создания записи и последнего изменения PGN. В API используются `createdAt` и `updatedAt` |

### Поиск и сортировка

Для поиска используются имена игроков из заголовков PGN. В v1 список сортируется от новых записей к старым. При совпадении времени создания записи сортируются по убыванию идентификатора. Для этого порядка предусмотрен составной индекс.

## Валидация данных

Контракт v1 задаёт правила проверки идентификатора, тела запроса и текста PGN.

### Идентификатор партии

`id` – положительное целое число в диапазоне от 1 до 2 147 483 647. Некорректный идентификатор даёт `400`. Если партии с допустимым идентификатором нет, контракт предусматривает `404 GAME_NOT_FOUND`.

### PGN

При создании и замене партии запрос содержит JSON-объект с единственным строковым полем `pgn`. Сервер отклоняет пустой или пробельный текст, начальный BOM, NUL и непарные суррогаты Unicode. Размер PGN проверяется в байтах UTF-8. Для тела HTTP-запроса действует отдельный предел, поскольку JSON-экранирование увеличивает его размер.

Сервер будет разбирать начальные заголовки до текста ходов. Допускаются LF и CRLF, а пустая строка перед ходами необязательна. Имена тегов состоят из латинских букв. При разборе имён учитывается регистр, повторяющиеся теги отклоняются. Значения тегов должны быть непустыми, без двойных кавычек, обратной косой черты и управляющих символов.

Значения по умолчанию для отсутствующих тегов

- `White`, `Black`, `Event` – `?`.
- `Date` – `????.??.??`.
- `Result` – `*`.

В теге `Date` проверяется формат `YYYY.MM.DD`. Неизвестный год обозначается `????`, неизвестный месяц или день – `??`. Допустимые значения `Result` – `1-0`, `0-1`, `1/2-1/2` и `*`. Значения по умолчанию записываются только в метаданные. Исходный PGN сохраняется без изменений.

## Обработка ошибок

| Статус | Код ошибки | Причина |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Некорректный параметр, JSON, состав полей или значение PGN |
| `404` | `GAME_NOT_FOUND` | Партия с допустимым идентификатором отсутствует |
| `404` | `NOT_FOUND` | Запрошен неизвестный маршрут API |
| `413` | `PAYLOAD_TOO_LARGE` | Превышен допустимый размер тела запроса |
| `429` | `TOO_MANY_REQUESTS` | Превышена допустимая частота запросов |
| `500` | `INTERNAL_ERROR` | Внутренняя ошибка сервера |

Ответ с ошибкой содержит `code` и русскоязычное сообщение `message`. Каждому лишнему полю JSON соответствует отдельный элемент `details`. Nginx возвращает согласованные JSON-ответы при превышении размера и частоты запросов. Другие ошибки прокси могут прийти в ином формате.

## Работа с датами и UTC

Дата партии хранится как текст, поскольку в PGN могут быть неизвестны год, месяц или день. Служебные даты `createdAt` и `updatedAt` передаются в UTC в формате ISO 8601 с суффиксом `Z`. При создании они равны. Время создания сохраняется при замене партии, а `updatedAt` обновляется только при изменении текста PGN.

## Версионирование API

Express использует версионный префикс для внутренних маршрутов API.

```text
/api/v1
```

На сервере Nginx передаёт запросы с `/chess-station/api/v1` во внутренний `/api/v1`. В `openapi.yaml` публичный префикс задан в `servers.url`, а пути операций в `paths` указаны относительно него. Несовместимый контракт можно будет опубликовать под префиксом `v2`, сохранив адреса v1 для существующих клиентов.

## Операции API

В таблице приведены маршруты Express и статусы по контракту v1. До подключения обработчиков партий запрос `GET /api/v1/games` возвращает `404 NOT_FOUND`.

| Метод | Путь | Описание | Успех | Ошибки |
|---|---|---|---|---|
| `GET` | `/api/v1/games` | Список партий с числом совпадений и параметрами пагинации | `200` | `400`, `429`, `500` |
| `POST` | `/api/v1/games` | Создание партии из PGN. Ответ содержит партию с присвоенным идентификатором | `201` | `400`, `413`, `429`, `500` |
| `GET` | `/api/v1/games/{id}` | Получение партии с исходным PGN | `200` | `400`, `404`, `429`, `500` |
| `PUT` | `/api/v1/games/{id}` | Полная замена PGN. Ответ содержит обновлённую партию | `200` | `400`, `404`, `413`, `429`, `500` |
| `DELETE` | `/api/v1/games/{id}` | Физическое удаление партии. Ответ без тела | `204` | `400`, `404`, `429`, `500` |

Операция `PUT` работает с существующей партией. При параллельной правке действует последняя успешная запись.

## Параметры списка партий

| Параметр | Назначение |
|---|---|
| `player` | Регистронезависимый поиск буквальной подстроки в имени белых или чёрных |
| `page` | Номер страницы. При отсутствии параметра используется `1` |
| `limit` | Размер страницы от `1` до `100`. При отсутствии параметра используется `20` |

Пробельные символы по краям `player` удаляются. Если значение пустое, фильтр по имени не применяется. Поиск поддерживает кириллицу и латиницу. Процент, подчёркивание и обратная косая черта ищутся как обычные символы. NUL и непарные суррогаты Unicode не допускаются.

Если номер страницы выходит за пределы результатов, ответ содержит пустой список и общее число совпадений. Некорректный номер или размер страницы приводит к `400`.

## OpenAPI

Файл `openapi.yaml` является формальным источником описания API. В нём зафиксированы базовый URL, операции, параметры запросов, схемы тела запроса и ответа, HTTP-статусы и схема ошибки. Контракт можно использовать для проверки совместимости и подключения внешних клиентов. [openapi.yaml](./openapi.yaml)

## Интерактивная документация API

После запуска backend интерактивная документация доступна по адресу:

```text
http://127.0.0.1:3001/api-docs/
```

Swagger UI визуализирует существующую спецификацию `openapi.yaml`. Через интерфейс можно просматривать описание операций, схемы запросов и ответов, а также отправлять тестовые запросы через кнопку «Try it out».

В спецификации используется относительный URL из `servers.url`. Запросы Swagger UI отправляются на тот же сайт, на котором открыта документация. При локальном запуске `OPENAPI_SERVER_URL=/api/v1` подставляет внутренний префикс в Swagger UI и YAML, который Express выдаёт по адресу `http://127.0.0.1:3001/openapi.yaml`. На сервере переменная пуста и действует публичный префикс из `openapi.yaml`. Файл в репозитории сохраняет публичный префикс.

## Переменные окружения

Для первого локального запуска создайте файл `.env` на основе `.env.example`.


## Развёртывание

ChessStation развёрнут по пути `/chess-station/` на сервере, где уже работает Система заметок с тегами ([http://201.34.159.85/notes/](http://201.34.159.85/notes/)), разработанная в рамках курсового проекта прошлого семестра. Чтобы сохранить доступность системы заметок при развёртывании ChessStation, его маршруты заданы в отдельном файле конфигурации Nginx. Nginx обслуживает статическую сборку веб-интерфейса и передаёт запросы к API и документации в Express.

Серверное приложение размещено в `/opt/chess-station-api`. Зависимости устанавливаются командой `npm ci --omit=dev`. Служба `chess-station-api.service` запускает `src/server.js` отдельным экземпляром Node.js 24.22.3 из `/opt/chess-station-api/runtime/bin/node`. Для службы включён автозапуск. Она работает от динамического пользователя `chess-station`.

Служба задаёт `NODE_ENV=production` и `PORT=3002` в окружении. Express слушает только `127.0.0.1:3002`. Пустое значение `OPENAPI_SERVER_URL` сохраняет публичный префикс в Swagger UI.

На сервере установлен PostgreSQL 18.6. При реализации хранения партий для ChessStation будут созданы отдельная база со схемой v1 и роль без прав суперпользователя.

Веб-сборка размещена в `/var/www/chess-station`. Маршруты заданы в `/etc/nginx/snippets/chess-station-locations.conf`.

| Публичный путь | Внутренний путь Express |
|---|---|
| `/chess-station/api/v1` | `/api/v1` |
| `/chess-station/api-docs/` | `/api-docs/` |
| `/chess-station/openapi.yaml` | `/openapi.yaml` |

При замене префикса сохраняется путь операции API или ресурса Swagger UI.

Nginx ограничивает размер тела запроса и частоту обращений к API.

- Размер тела запроса – до 2 МиБ. При превышении Nginx возвращает `413 PAYLOAD_TOO_LARGE`.
- Частота запросов – 10 в секунду на IP-адрес. Настройка `burst=20 nodelay` допускает до 20 избыточных запросов без задержки при кратковременном всплеске. При исчерпании допуска Nginx возвращает `429 TOO_MANY_REQUESTS`.

Оба ответа содержат русскоязычное сообщение в формате API.

Перед изменением конфигурации Nginx сохраняют её копию и проверяют новую конфигурацию командой `nginx -t`. После обновления проверяют веб-интерфейс, Swagger UI, выдачу OpenAPI и доступность Notes.

## Демонстрационные данные

Для v1 предусмотрен набор из 45–50 классических партий. Перед загрузкой через локальный API каждую партию проверят по правилам импорта веб-редактора.

Команда ручного восстановления будет очищать таблицу ChessStation и загружать демонстрационный набор заново. Добавленные посетителями партии при восстановлении удаляются. Команду запускает владелец сервера.

## Ручная проверка серверной части

### Текущая версия

1. Запустить Express через `npm start`.
2. Открыть Swagger UI и спецификацию OpenAPI на локальном адресе.
3. Проверить, что при `OPENAPI_SERVER_URL=/api/v1` Swagger UI использует внутренний префикс, а опубликованная документация – `/chess-station/api/v1`.
4. Выполнить `GET /api/v1/games` локально. До подключения обработчиков партий ожидается `404 NOT_FOUND`.

### После реализации v1

1. Проверить все пять операций и статусы по OpenAPI.
2. Создать партию и сравнить полученный PGN с исходным текстом, а метаданные – с заголовками.
3. Повторить `PUT` с тем же PGN и проверить, что `updatedAt` не изменился. Затем заменить PGN и проверить, что `createdAt` сохранился, а `updatedAt` обновился.
4. Проверить поиск по именам белых и чёрных на кириллице и латинице. Убедиться, что `%`, `_` и обратная косая черта ищутся буквально.
5. Проверить, что партии с одинаковым временем создания идут по убыванию идентификатора.
6. Запросить страницу за пределами результатов. Список должен быть пустым, а число совпадений – соответствовать фильтру.
7. После размещения проверить Swagger UI, доступность Notes и ответы прокси при превышении лимитов.

## Преимущества архитектуры v1

- Исходный PGN можно вернуть без изменений при чтении и экспорте партии.
- Поиск по метаданным не требует повторного разбора PGN.
- Исходный текст и метаданные сохраняются одной операцией, поэтому ошибка не оставляет частично обновлённую запись.

## Недостатки первой версии

- Через API можно будет сохранить партию, которую веб-редактор не сможет открыть для редактирования. Для такой партии доступны исходный PGN, экспорт и удаление.
- При одновременной правке последнее успешное сохранение заменяет предыдущую версию партии.
- Посетители смогут менять и удалять партии демонстрационного набора. Добавленные ими записи будут удалены при восстановлении набора.

## Изначально заложенные ограничения

- Поиск по именам игроков. Для поиска по ходам и позициям потребуется разбирать запись ходов и воспроизводить сохранённые партии.
- Проверка заголовков PGN на сервере. Легальность ходов в v1 проверяет веб-редактор при вводе и воспроизведении.
- Демонстрация без учётных записей и разграничения доступа к партиям.
- Защита от одновременной перезаписи, автоматическое резервное копирование, массовый импорт и поиск дубликатов выходят за пределы v1.

## Изначально заложенная расширяемость

- HTTP-контракт отделяет клиентские приложения от схемы PostgreSQL. Пока контракт соблюдается, можно менять SQL-запросы и структуру хранения без изменений в клиентах.
- Исходный PGN позволяет повторно извлечь метаданные и построить индекс позиций для уже сохранённых партий.
- Сервисный слой отделяет проверку PGN от обработки HTTP. Проверку ходов можно будет добавить в операции создания и замены партии без изменения маршрутизации.

## Концепция и перспективы развития

### Другие интерфейсы ChessStation

Браузер – один из способов работы с ChessStation. К HTTP API можно подключить приложение для компьютера и мобильное приложение. Утилита командной строки сможет искать партии и выгружать PGN. Интерактивный терминальный интерфейс сможет отображать доску и фигуры текстовыми символами и принимать команды с клавиатуры. Для всех этих клиентов доступ к PostgreSQL обеспечивает сервер.

### Серверная проверка легальности ходов

В следующих версиях сервер будет проверять легальность ходов при создании и замене партии независимо от того, какой клиент отправил PGN. Для этого серверу потребуется воспроизводить присланную последовательность ходов. В контракте нужно будет определить ответ при обнаружении нелегального хода и порядок работы с партиями, сохранёнными до введения проверки. Веб-редактор продолжит проверять ход при вводе, до отправки PGN на сервер.

### Поиск, дебюты и репертуар

Расширенный поиск охватит события, даты, ходы, дебюты и позиции. Для поиска по позиции потребуется воспроизвести партии и построить индекс. Он позволит находить одинаковую позицию при разном порядке ходов. Дебютный справочник свяжет названия систем с партиями, а дебютные деревья покажут частоту продолжений и результаты по отобранным партиям. Личный репертуар будет хранить линии, которые пользователь выбирает для игры за белых и чёрных.

### Позиции, варианты и анализ движком

FEN позволит обмениваться отдельными позициями, а редактор расстановки – задавать их независимо от сыгранной партии. Для вариантов понадобится хранить несколько продолжений из одной позиции и связывать с ними комментарии и графические пометки. Шахматный движок позволит оценивать позиции и находить сильные продолжения. Результаты анализа можно хранить отдельно от исходного PGN и связывать с нужной позицией.

### Подготовка, обучение и публикация

Отчёт о сопернике сможет показывать его дебюты, частые продолжения и результаты за белых и чёрных со ссылками на партии, по которым рассчитана статистика. Позиции из партий и линии репертуара можно будет использовать в упражнениях. Разбор партии можно будет публиковать с вариантами и комментариями и передавать в PGN.
