# ChessStation API

ChessStation – шахматная информационно-аналитическая система. В этом репозитории разрабатывается серверная часть. В первой версии она хранит партии в PostgreSQL и предоставляет HTTP API для работы с ними.

Репозиторий веб-интерфейса – [chess-station-web](https://github.com/b0x009dev/chess-station-web).

## Назначение проекта

Через API веб-клиент сохраняет партии, ищет их по имени игрока и загружает PGN для просмотра, редактирования и экспорта. При запросе списка сервер возвращает имена игроков, событие, дату и результат без текста PGN.

## Серверная часть в архитектуре ChessStation

- `chess-station-api` обрабатывает HTTP-запросы, проверяет заголовки PGN, ищет и сохраняет партии.
- `chess-station-web` показывает список партий и редактор, проверяет ходы, импортирует и экспортирует файлы в браузере.
- PostgreSQL хранит исходный PGN, сведения для списка и служебные даты.
- Nginx отдаёт статические файлы веб-интерфейса и передаёт обращения к API серверному приложению.

Веб-интерфейс обращается к серверу по HTTP и обменивается с ним данными в JSON. Доступом к PostgreSQL управляет серверное приложение. Запросы, ответы и ошибки описаны в `openapi.yaml`.

## Основные возможности

- Выдача списка партий с поиском по имени белых или чёрных и пагинацией.
- Получение партии по идентификатору. Ответ содержит исходный PGN.
- Создание, полная замена PGN сохранённой партии и удаление партии.
- Извлечение имён белых и чёрных, события, даты и результата из заголовков PGN.
- Проверка параметров и тела запроса, единый формат ошибок.
- Описание API в OpenAPI и интерактивная документация Swagger UI.

Импорт и экспорт файлов выполняются в браузере. Для сохранения импортированной партии клиент использует тот же запрос, что и для партии, составленной на доске.

## Обоснование выбранного стека

Сервер работает в Node.js. Express сопоставляет запросы с маршрутами, разбирает JSON и передаёт ошибки централизованному обработчику. Сервис проверяет заголовки PGN независимо от HTTP-обработчиков.

PostgreSQL хранит партии между перезапусками сервиса и выполняет поиск, сортировку и пагинацию. В первой версии используется одна таблица, а операции сводятся к чтению списка и работе с отдельной партией. Для этих операций достаточно прямых SQL-запросов. Входные значения передаются в PostgreSQL как параметры.

Swagger UI строит интерактивную документацию по `openapi.yaml`. Через неё можно отправлять запросы к серверу и проверять ответы без запуска веб-интерфейса.

## Архитектура серверной части

- Маршруты связывают HTTP-метод и путь с контроллером.
- Контроллеры получают параметры и тело запроса, вызывают сервис и формируют HTTP-ответ.
- Сервисы проверяют данные, разбирают заголовки PGN и подготавливают сведения для сохранения.
- Слой доступа к данным выполняет параметризованные запросы к PostgreSQL.
- Конфигурация задаёт параметры подключения к PostgreSQL и настройки HTTP-сервера.
- Обработка ошибок определяет HTTP-статус и формирует тело ошибки.

При создании партии и замене PGN сервис применяет одни и те же правила. После проверки он передаёт исходный текст и значения заголовков в слой доступа к данным. Для списка сервер выбирает метаданные. Одно и то же условие поиска используется для выборки партий и подсчёта совпадений.

## Структура проекта

`src/app.js` настраивает Express, публикацию спецификации и Swagger UI. `src/server.js` читает порт из окружения и запускает HTTP-сервер. Маршруты, контроллеры, сервисы и SQL-запросы размещаются в `src/routes/`, `src/controllers/`, `src/services/` и `src/repositories/` соответственно. Контракт `openapi.yaml` находится в корне репозитория.

## Модель данных

Первая версия использует одну таблицу `games`. Идентификатор партии назначает PostgreSQL. Один и тот же PGN может быть сохранён в нескольких записях.

- `id` – целочисленный первичный ключ партии.
- `pgn` – исходный текст партии.
- `white`, `black`, `event`, `result` – имена игроков, событие и результат.
- `game_date` – дата партии в текстовом формате PGN. В API – `date`.
- `created_at`, `updated_at` – время создания и последнего изменения PGN. В API – `createdAt`, `updatedAt`.

Дата партии хранится как текст, поскольку в PGN могут быть неизвестны год, месяц или день. API возвращает `createdAt` и `updatedAt` в UTC в формате ISO 8601 с суффиксом `Z`. При создании они равны. Время создания сохраняется при любой замене, а `updatedAt` обновляется только при изменении текста PGN.

При создании или замене партии сервер извлекает значения заголовков PGN. Затем исходный текст и извлечённые значения сохраняются одним SQL-запросом. Для поиска используются уже записанные имена игроков.

### Поиск, сортировка и пагинация

Поиск выполняется по подстроке в имени белых или чёрных без учёта регистра и поддерживает кириллицу и латиницу. Процент, подчёркивание и обратная косая черта ищутся как обычные символы.

Партии выдаются от новых к старым по времени создания. При совпадении времени первой идёт партия с большим идентификатором. Составной индекс соответствует этому порядку. Общее число совпадений вычисляется по тем же условиям поиска до разбиения на страницы.

## Проверка PGN

При создании и замене партии запрос содержит JSON-объект с единственным строковым полем `pgn`. Сервер проверяет тип и размер значения `pgn`. Пустой или пробельный текст, начальный BOM, NUL и непарные суррогаты Unicode отклоняются. Размер PGN в байтах UTF-8 проверяется отдельно от размера HTTP-тела, который зависит и от JSON-экранирования.

Сервер разбирает начальные заголовки до текста ходов. Допускаются LF и CRLF, а пустая строка перед ходами необязательна. В именах тегов допускаются только латинские буквы. При разборе имён сервер учитывает регистр и отклоняет повторяющиеся теги. Значения тегов должны быть непустыми, без двойных кавычек, обратной косой черты и управляющих символов. Сервер проверяет формат `Date` и допустимость значения `Result`.

Если тег имени или события отсутствует, в метаданные записывается `?`. Для отсутствующей даты используется `????.??.??`, для отсутствующего результата – `*`. Тег с пустым значением отклоняется. Значения по умолчанию применяются только к метаданным. Принятый PGN сохраняется в исходном виде.

В первой версии сервер не проверяет легальность ходов. Веб-редактор проверяет, соответствует ли PGN поддерживаемому формату, и воспроизводит партию ход за ходом. Если сохранённый PGN не проходит проверку редактора, остаются доступны просмотр исходного PGN, его экспорт и удаление партии.

## Версионирование API

`v1` обозначает версию контракта HTTP API. Контракт определяет доступные операции, параметры запросов, структуру ответов и формат ошибок. Публичный префикс первой версии – `/chess-station/api/v1`. Nginx передаёт запросы в Express, который обслуживает внутренний префикс `/api/v1`.

Для новой версии с несовместимым контрактом можно выделить отдельный префикс `v2`.

## HTTP API

Пути операций указаны без префикса API.

- `GET /games` возвращает `200` со страницей списка, числом совпадений и параметрами пагинации.
- `GET /games/{id}` возвращает `200` с данными партии, включая исходный PGN.
- `POST /games` возвращает `201` с полными данными созданной партии и её новым идентификатором.
- `PUT /games/{id}` возвращает `200` с полными данными обновлённой партии.
- `DELETE /games/{id}` возвращает `204` без тела после физического удаления партии.

Для поиска по имени игрока в запросе списка используется `player`, для пагинации – `page` и `limit`. Если `player` отсутствует или пуст после удаления пробельных символов по краям, сервер возвращает партии без фильтра по игроку. Если допустимый номер страницы выходит за пределы результатов, сервер возвращает пустой список и общее число совпадений. При недопустимом номере или размере страницы сервер возвращает `400`.

При `PUT` клиент передаёт полный PGN сохранённой партии. Если указанная партия отсутствует, сервер возвращает `404`. При параллельном редактировании действует последняя успешная запись.

### Обработка ошибок

- `400` `VALIDATION_ERROR` – некорректный параметр, JSON, состав полей или значение PGN.
- `404` `GAME_NOT_FOUND` – партия с допустимым идентификатором отсутствует.
- `404` `NOT_FOUND` – запрошен неизвестный маршрут API.
- `413` `PAYLOAD_TOO_LARGE` – превышен допустимый размер HTTP-тела.
- `429` `TOO_MANY_REQUESTS` – превышена допустимая частота запросов.
- `500` `INTERNAL_ERROR` – внутренняя ошибка сервера.

Ответ с ошибкой содержит `code` и русскоязычное сообщение `message`. Каждому лишнему полю JSON соответствует отдельный элемент `details`. Nginx возвращает согласованные JSON-ответы при превышении размера и частоты запросов. Другие ошибки прокси могут прийти в ином формате.

## Локальный запуск

Для запуска используется Node.js 24. Локально проверены Node.js 24.15.0 и npm 11.12.1.

1. Установить зависимости командой `npm ci`.
2. Скопировать `.env.example` в `.env`.
3. Запустить сервер командой `npm start`.

Express принимает запросы на `127.0.0.1`. При порте `3001` Swagger UI доступен по `http://127.0.0.1:3001/api-docs/`, спецификация – по `http://127.0.0.1:3001/openapi.yaml`.

### Переменные окружения

Начальные значения заданы в `.env.example`.

- `PORT=3001` – порт HTTP-сервера.
- `OPENAPI_SERVER_URL=/api/v1` – базовый путь для запросов из Swagger UI.
- `PGHOST=127.0.0.1` – адрес PostgreSQL.
- `PGPORT=5432` – порт PostgreSQL.
- `PGDATABASE=chess_station` – имя базы для партий.
- `PGUSER=chess_station` – имя роли PostgreSQL.
- `PGPASSWORD=` – пароль роли. В шаблоне поле оставлено пустым.

При пустом `OPENAPI_SERVER_URL` используется публичный путь из `openapi.yaml`. Настройка влияет на Swagger UI и на спецификацию, которую возвращает Express. Исходный файл в репозитории сохраняет публичный путь.

Переменные `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER` и `PGPASSWORD` понадобятся при подключении операций с партиями. Для запуска Express и просмотра документации достаточно настроек HTTP.

### Проверка кода

Команда `npm run lint` проверяет JavaScript по рекомендованным правилам ESLint для проекта на Node.js.

## Развёртывание рядом с Notes

ChessStation будет размещён по пути `/chess-station/` на сервере `201.34.159.85`, где уже опубликована Система заметок с тегами ([http://201.34.159.85/notes/](http://201.34.159.85/notes/)) – курсовой проект прошлого семестра. Для ChessStation предусмотрен публичный доступ по HTTPS. Nginx отдаёт статические файлы веб-интерфейса и проксирует запросы к API, Swagger UI по `/chess-station/api-docs/` и OpenAPI по `/chess-station/openapi.yaml`.

На сервере проверяют наличие Node.js 24 и выбирают свободный порт для Express. Порт `3001` указан в `.env.example`. В конфигурации Nginx задают тот же порт, что и в серверном `.env`. Зависимости устанавливают командой `npm ci --omit=dev`. Express запускают через `npm start` из каталога репозитория отдельной службой systemd с автозапуском. Пользователю службы нужны права на чтение файлов приложения и `.env`. В серверном `.env` `OPENAPI_SERVER_URL` оставляют пустым, чтобы Swagger UI использовал публичный путь.

Маршруты прокси задают в HTTPS-конфигурации Nginx.

- `/chess-station/api/v1` проксируется в `/api/v1`.
- `/chess-station/api-docs/` проксируется в `/api-docs/`.
- `/chess-station/openapi.yaml` проксируется в `/openapi.yaml`.

Nginx сохраняет оставшуюся часть пути при проксировании запросов к API и ресурсов Swagger UI. Для API предусмотрены предел тела запроса 2 МиБ и ограничение 10 запросов в секунду на IP-адрес с допуском до 20 запросов сверх этой частоты. При превышении предела Nginx возвращает `413 PAYLOAD_TOO_LARGE`, при превышении частоты – `429 TOO_MANY_REQUESTS`. Оба ответа содержат русскоязычное сообщение в формате API.

Перед применением сохраняют копию действующей конфигурации Nginx и проверяют новую командой `nginx -t`. После запуска службы проверяют Swagger UI, выдачу OpenAPI, ответы API через прокси и доступность Notes. Для операций с партиями предусматриваются отдельная база PostgreSQL и роль без прав суперпользователя.

## Демонстрационные данные

Для демонстрации предусмотрено 45–50 классических партий. Перед загрузкой через локальный API каждую партию проверяют по правилам импорта веб-редактора.

Ручное восстановление удаляет текущие записи только из базы ChessStation, включая добавленные пользователями партии, и снова загружает демонстрационные данные. Эту операцию выполняет владелец сервера.

## Ручная проверка серверной части

Проверяются все пять операций и соответствие ответов контракту. При чтении исходный PGN должен совпасть с сохранённым текстом, а метаданные – с заголовками. При замене PGN время создания остаётся прежним. Повторный `PUT` с точно таким же PGN сохраняет `updatedAt`. Если текст изменился, `updatedAt` обновляется.

Поиск проверяют по именам белых и чёрных на кириллице и латинице, включая ввод символов `%`, `_` и обратной косой черты. Для партий с одинаковым временем создания проверяют порядок по идентификатору. Запрос страницы за пределами результатов должен вернуть пустой список и верное число совпадений. После размещения проверяются Swagger UI, ответы прокси при превышении лимитов и доступность Notes.

## Преимущества архитектуры

Хранение исходного PGN позволяет вернуть тот же текст при чтении и экспорте партии. В списке используются отдельно сохранённые метаданные, поэтому PostgreSQL ищет партии по именам без разбора PGN. Запись текста и метаданных одной операцией исключает частичное обновление при сохранении партии.

## Недостатки первой версии

Некоторые партии, сохранённые через API, в браузере можно только просмотреть, экспортировать или удалить. При параллельной правке полная замена может перезаписать чужие изменения. Демонстрационная база открыта для записи, поэтому посетители могут менять и удалять партии. Ручное восстановление возвращает демонстрационный набор. Пользовательские записи при восстановлении теряются.

## Изначально заложенные ограничения

Поиск в первой версии ограничен именами игроков, которые сервер извлекает из заголовков PGN при сохранении. Для поиска по ходам и позициям потребуется обработать записи ходов и воспроизвести сохранённые партии.

При сохранении сервер проверяет запрос и заголовки PGN. Легальность ходов проверяет веб-редактор при вводе и воспроизведении. Из-за различия в проверках через API можно сохранить PGN партии, которую браузерный редактор не сможет открыть для правки. Проверка легальности на сервере относится к следующим версиям.

Демонстрация доступна без учётной записи. Разделение пользовательских данных, защита от параллельной записи, автоматическое резервирование, массовый импорт и проверка дубликатов выходят за границы первой версии.

## Изначально заложенная расширяемость

API отделяет пользовательские интерфейсы от схемы PostgreSQL. Пока контракт сохраняется, SQL-запросы и схему хранения можно менять внутри сервера. Исходный PGN позволяет заново извлечь метаданные или построить индекс позиций для уже сохранённых партий.

## Концепция и перспективы развития

### Другие интерфейсы ChessStation

Браузер – один из способов работы с ChessStation. К HTTP API можно подключить приложение для компьютера и мобильное приложение. Утилита командной строки сможет искать партии и выгружать PGN. Интерактивный терминальный интерфейс сможет отображать доску и фигуры текстовыми символами и принимать команды с клавиатуры. Для всех этих клиентов доступ к PostgreSQL обеспечивает сервер.

### Серверная проверка легальности ходов

В следующих версиях сервер будет проверять легальность ходов при создании и замене партии независимо от того, какой клиент отправил PGN. Для этого серверу потребуется воспроизводить присланную последовательность ходов. В контракте нужно будет определить ответ при обнаружении нелегального хода и порядок работы с партиями, сохранёнными до введения проверки. Веб-редактор продолжит проверять ход при вводе, до отправки PGN на сервер.

### Поиск, дебюты и репертуар

Расширенный поиск охватит события, даты, ходы, дебюты и позиции. Для поиска по позиции потребуется воспроизвести партии и построить индекс. Он позволит находить одинаковую позицию при разном порядке ходов. Дебютный справочник свяжет названия систем с партиями, а дебютные деревья покажут частоту продолжений и результаты по отобранным партиям. Личный репертуар будет хранить линии, которые пользователь выбирает для игры за белых и чёрных.

### Позиции, варианты и анализ движком

FEN позволит обмениваться отдельными позициями, а редактор расстановки – задавать их независимо от сыгранной партии. Для вариантов понадобится хранить несколько продолжений из одной позиции и связывать с ними комментарии и графические пометки. Шахматный движок позволит оценивать позиции и находить сильные продолжения. Результаты анализа можно хранить отдельно от исходного PGN и связывать с нужной позицией.

### Подготовка, обучение и публикация

В отчёте о сопернике можно будет посмотреть его дебюты, наиболее частые продолжения и результаты отдельно за белых и чёрных, а затем открыть партии, по которым рассчитана статистика. Разобранные позиции и линии репертуара можно будет включать в упражнения. Разбор партии можно будет опубликовать с вариантами и комментариями. Партиями можно будет обмениваться в PGN.
